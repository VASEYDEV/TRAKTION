# Milestone 1 audit — 2026-09-03

## Decision

**Pass with follow-up.** The implemented Milestone 1 contract—offline,
supplied-order vertical reconstruction of 2–10 equal-width opaque PNG captures—
has reproducible exact-pixel and fail-closed evidence. Sequence intelligence
must remain out of the shipping path until its own task defines graph-level
ambiguity and budget semantics. The broader evaluation matrix and peak-memory
instrumentation are evidence gaps to close alongside, not silent capabilities
to claim.

## Evidence reviewed

- Tasks 0001–0005 and the implementation and tests they reference.
- `ReconstructionEngine`, `ReconstructionSettings`, the pure/Apple PNG boundary,
  FixtureForge control-set generator, Lab manifests, and evaluation harness.
- The current 67-test Swift suite, portable PNG smoke, repository policy check,
  and standard 16-case evaluation report.
- ADR-011 through ADR-013 and the product invariants in `AGENTS.md`.

## 1. Completed capabilities

- The engine validates the Milestone 1 axis, capture-count, width, duplicate,
  input-pixel, overlap-search, comparison, and output-pixel bounds with typed
  failures before publishing a result.
- Registration requires one uniquely acceptable, fully scored translation.
  Adaptive early-exit work only rejects a candidate after a monotonic lower
  bound exceeds an unchanged acceptance threshold; unresolved work still fails
  closed on its comparison budgets.
- Reconstruction planning uses half-open source spans and rendering makes one
  final allocation. Existing exact controls compare the final RGBA raster to
  the known source canvas.
- PNG decode/encode and the Lab reconstruction path work on Linux through the
  dependency-free fallback; Apple ImageIO remains behind the same adapter.
- Failure manifests and evaluation reports are Codable, machine-readable, and
  exercised through command-line smoke/evaluation paths.

## 2. Missing or partial capabilities

These are not regressions against the narrow Milestone 1 runtime contract:

- The evaluation corpus does not yet separately label all fixture categories in
  `docs/EVALUATION.md`: light text, dark UI, mixed photography, tables/thin
  rules, monospaced code, dynamic regions, and compressed-source inputs are not
  represented as distinct standard cases.
- Approximate evaluation records registration and seam energy, but OCR and edge
  continuity metrics are not implemented.
- Golden failures do not currently publish the complete CI artifact bundle
  described by the evaluation plan (expected, actual, absolute difference,
  manifest, and joint diagnostics).
- Peak memory, preview latency, export throughput, and very-long-canvas behavior
  are not instrumented. Existing performance tests prove bounded practical
  execution shapes rather than stable latency service levels.
- Real-world fixture storage is intentionally empty/private, so the current
  evidence is deterministic and synthetic rather than device-capture diverse.

## 3. Golden-test status

The portable Swift gate passed all 67 discovered tests. Coverage includes exact
reconstruction, row accounting, determinism, repeated/ambiguous content,
resource-limit failures, the adversarial control set, pure PNG behavior, codec
parity contracts, and phone-scale registration. The standard evaluation corpus
reported 16/16 passes with zero false-safe, false-warning, wrong-failure, or
nondeterministic outcomes.

## 4. False-safe findings

No false-safe was reproduced in the current standard corpus. Code inspection
confirmed that refinement does not select from a truncated candidate list: if
all plausible translations cannot be fully verified within both candidate and
pixel budgets, registration returns `resourceLimitExceeded`. Genuine periodic
ambiguity retains multiple exact candidates and returns `ambiguousOverlap`.

This is evidence for the tested input families, not a claim of a zero general
false-safe rate. The missing visual categories above and absence of a private
real-device qualification corpus limit that claim.

## 5. Performance and memory concerns

- Default budgets permit up to 128 Mi pixel comparisons in sampling/refinement
  and 64 Mi pixels in final candidate scoring per joint. These are explicit
  compute bounds, but elapsed time will vary by device.
- Row-energy ordering allocates an integer per capture row and sorts it; row
  hashes allocate one 64-bit value per row. Both are modest relative to RGBA
  storage under current capture limits.
- The engine retains all input rasters and allocates the complete output raster.
  No measured peak-memory gate currently verifies the resulting amplification.
- Evaluation runs each case twice for determinism while timing only the first
  run; the reported milliseconds are diagnostic and intentionally not used as a
  deterministic acceptance threshold.

## 6. Privacy and security changes

Tasks 0004 and 0005 introduced no network path, provider SDK, credential input,
source deletion, or source overwrite. Evaluation fixtures are generated in
process from fixed seeds. The Lab writes only to an explicit output path and
retains existing no-overwrite/clean-retry publication behavior.

## 7. Architecture drift from ADRs

No blocking drift was found. Core owns registration, seam selection, planning,
and pixels; FixtureForge owns deterministic fixture generation; the Lab calls
shipping core code; and the optional AI target remains a protocol/adapter
boundary without pixel mutation. ADR-013 records the adaptive-verification
strategy and unchanged fail-closed semantics.

One documentation caveat is worth preserving: `refinementRounds` is a
compatibility/configuration switch—`1` disables adaptive verification and all
values at or above `2` currently run the same single refinement pass. It should
not be presented as multiple iterative rounds.

## 8. Technical debt and Milestone 2 entry criteria

Before automatic ordering becomes shipping behavior, its tracked task must:

1. Define a deterministic pairwise-edge score and a global uniqueness rule;
   local best matches alone may not choose documentary order.
2. Preserve the existing supplied-order entry point and its exact output as a
   compatibility path.
3. Bound graph construction and verification for 2–10 captures with
   overflow-safe accounting and typed resource failures.
4. Distinguish duplicate input, disconnected/missing coverage, reversible
   ambiguity, and genuinely unique order without silently bridging a gap.
5. Add permutation, duplicate, repeated-content, missing-middle, and
   determinism goldens, including a test proving the ambiguity gate can fail.
6. Expand the standard evaluation report with ordering metrics before claiming
   Milestone 2 completion.

In parallel, expand the synthetic corpus categories and add a platform-credible
peak-memory measurement strategy. Neither should be hidden behind skipped tests.

## 9. Recommendation

Accept Milestone 1 **with the follow-ups above recorded as evidence work**. Begin
Milestone 2 only through a new task packet and ADR if its public contract changes;
do not edit `AGENTS.md` for that work. The existing canonical contract already
states the correct invariants and should remain stable.
